## Идея

На CPU время PINN 256×4 определяется умножением матриц 256×256 (395 тыс. операций на запрос). Оптимизации:

1. **Дистилляция**: сети 128×4 и 64×4 учатся у PINN 256×4 (учителя) — на данных таблицы, на ответах учителя в случайных точках всей области и с теми же физическими штрафами.
2. **float16-веса** — вдвое меньше файл.
3. **ONNX Runtime** на CPU.
4. **Смешанная точность** на GPU (`torch.autocast`, матрицы во float16, log/pow/sinh во float32).
5. **SVD-сжатие внутренних слоёв** (5.4): каждая матрица 256×256 заменяется лучшим приближением ранга r — W ≈ (U_r S_r) V_rᵀ, два слоя 256→r→256; первый (2→256) и последний (256→2) слои не трогаются — они маленькие и критичны для физики. Затем «безопасный путь»: дообучение 1000 шагов с теми же физическими штрафами и исходной PINN в роли учителя.

## Результаты (пробное обучение учеников — 3000 шагов)

| | PINN 256×4 | 128×4 | 64×4 |
|---|---|---|---|
| файл float16 | 0,38 МБ | 0,10 МБ | **0,028 МБ** |
| ошибка P / e (медиана) | 0,23% / 0,25% | 3,6% / 4,2% | 5,7% / 3,8% |
| CPU, ONNX Runtime | 0,54 с | 0,18 с | **0,083 с** |
| GPU, float16 | 0,006 с | 0,004 с | 0,002 с |

Эффект относительно PINN 256×4 (float32, PyTorch, CPU): 128×4 — в 7,6 раза меньше и в 4,5 раза быстрее; 64×4 — в 27 раз меньше и в 9,9 раза быстрее (быстрее билинейной интерполяции). Смешанная точность на GPU ускоряет PINN 256×4 в 3,8 раза (ошибка P 0,23% → 0,39%). Учитель важен: на CPU 64×4 за 15 000 шагов с учителем — 2,5% по P, без учителя — 6,5%.

Время исходной PINN на CPU (ONNX) и GPU — из 5.3; дообучение — 17 с (r = 64) и 16 с (r = 32) на T4.

**Вывод.** Чистое SVD-сжатие внутренних слоёв разрушает физику модели: при r = 64 медианная ошибка давления вырастает с 0,23% до 17,7%, а условия устойчивости нарушаются в 11,6% (∂P/∂ρ ≤ 0) и 6,2% (∂e/∂T < 0) точек. Причина — веса не низкоранговые: первые 64 сингулярных числа несут лишь 85–90% Σσ². Короткое дообучение после SVD (1000 шагов, 17 с на T4) с теми же физическими штрафами восстанавливает свойства модели: нарушений снова 0%, медианная ошибка 0,33% по давлению и 0,40% по энергии — всего на 0,1–0,15 процентного пункта больше, чем у исходной PINN; 99-й перцентиль ошибки давления не ухудшился (2,53% против 2,59%). В итоге модель в 2 раза меньше (0,20 МБ во float16), инференс быстрее в 1,3 раза на CPU (ONNX) и в 1,4 раза на GPU. При r = 32 — сжатие в 4 раза при ошибке 0,43% / 0,50% и практически нулевых нарушениях.

SVD + дообучение на порядок точнее дистилляции при сопоставимом размере (сеть 128×4: 0,10 МБ и 3,6%), потому что стартует с весов обученной сети.

## Инференс на C (5.5)

На C перенесён только прямой проход уже обученной сети (`csrc/eos_pinn.c`, ~200 строк, без зависимостей кроме libm и OpenMP): нормировка входов → слои Linear + GELU → обратное преобразование в P и e. Обучение и производные через autograd остаются в PyTorch — переписывать их на C означает большую работу без выигрыша. Веса пишет `eos.cinfer.export_weights` (поддерживается и SVD-сжатая сеть), Python-обёртка `eos.cinfer.CEOS` имеет тот же `predict(rho, T)`; `csrc/example.c` — пример вызова из расчётного кода.

**Зачем.** Уравнение состояния в гидродинамических кодах вызывается из C/Fortran по одной точке на ячейку, миллионы раз на шаге по времени. Там важны задержка одного вызова и отсутствие зависимостей (Python, PyTorch, GPU), а не пакет из 10⁵ точек.

Замеры (CPU i5-13420H, каждый вариант в отдельном процессе, P-ядра; 10⁵ случайных точек):

| | PyTorch | ONNX Runtime | **C** |
|---|---|---|---|
| **1 запрос, PINN 256×4** | 114 мкс | 30 мкс | **15 мкс** (из Python — 14,5) |
| **1 запрос, SVD r = 64** | 120 мкс | 23 мкс | **7,3 мкс** |
| пакет 10⁵, 1 поток, 256×4 | 0,58 с | 0,46 с | 0,64 с |
| пакет 10⁵, 8 потоков, 256×4 | 0,20 с | 0,15 с | 0,18 с |
| пакет 10⁵, 8 потоков, SVD r = 64 | 0,16 с | 0,10 с | 0,10 с |

Точность совпадает с PyTorch до 6·10⁻⁶ (float32), ошибка на test та же: 0,226% / 0,246%.

**Вывод.** Одиночный запрос на C в 8 раз быстрее PyTorch и в 2 раза быстрее ONNX Runtime; вместе с SVD r = 64 — в 16 и 3 раза (7,3 мкс). Для расчётного кода это означает, что 10⁶ ячеек на шаге обрабатываются за ~7–15 мс на одном ядре без Python и GPU; программа весит 31 КБ, веса — 0,76 МБ (0,38 МБ для SVD). В пакетном режиме C на уровне ONNX Runtime и быстрее PyTorch на нескольких потоках; в один поток оптимизированное умножение матриц (MKL) не обогнать без собственного GEMM — это не цель: для пакетов есть GPU (0,013 с). Из оптимизаций на C: блок по 4 точки на строку весов (4 независимых накопителя FMA) и быстрая erf для GELU (погрешность 1,5·10⁻⁷) — задержка снизилась с 28 до 15 мкс.
